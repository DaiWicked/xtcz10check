# XTC ND03（小天才 Z10）解锁镜像对比分析报告

> 分析日期：2026-10-06
> 设备：小天才 Z10（代号 ND03），高通骁龙 W5 Gen1（SW5100），A/B 分区
> 原版固件：ND03_V2.8.1（2025-03-24 构建）
> 分析范围：原版固件 vs 作者解锁镜像 vs offline-files 刷机包

## 一、工作区文件总览

| 目录/文件 | 性质 | 说明 |
|---|---|---|
| `ND03-2025-03-24.../` | **原版官方固件** | 完整高通 EDL 线刷包，V2.8.1 |
| `2/250803/` | **作者解锁镜像** | abl/boot/super/vbmeta/vbmeta_system 五个镜像 |
| `2/` | 辅助工具 | fh_loader.exe、prog_firehose_ddr.elf、fastboot.img、recovery.img |
| `offline-files/` | **作者刷机包（带刷写脚本）** | 与 `2/250803/` 镜像哈希完全一致，外加 misc.img 和明文 rawprogram0.xml |
| `已解压文件（ai无需读取）/` | 压缩包备份 | 上述内容的 zip 原始包 |

### 关键关系确认
`2/250803/` 与 `offline-files/` 中的核心镜像 **SHA256 完全一致**，是同一套文件的两种命名方式：
- `2/250803/abl.img` = `offline-files/abl_a.img`
- `2/250803/boot.img` = `offline-files/boot_a.img`
- `2/250803/vbmeta.img` = `offline-files/vbmeta_a.img`
- `2/250803/vbmeta_system.img` = `offline-files/vbmeta_system_a.img`
- `2/250803/super.img` = `offline-files/super.img`

带 `_a` 后缀表示刷入 A/B 分区的 **A 槽位**。

### 2.2 misc.img（最关键发现！）

| 维度 | 原版 misc.mbn | 作者 misc.img |
|---|---|---|
| 大小 | 1 MB | **13 字节** |
| 格式 | 带高通签名头 | 纯 ASCII 文本 |
| 内容 | 签名+结构化数据 | **`boot-fastboot`** |

**十六进制：** `62 6F 6F 74 2D 66 61 73 74 62 6F 6F 74`

**技术含义：**
这是高通 Android 设备 misc 分区的标准启动命令。bootloader（abl）启动时会读取 misc 分区，如果开头是 `boot-fastboot` 命令字符串，设备会**直接进入 fastboot 模式**，而不是正常启动系统。

**作用：** 小天才手表没有方便的按键组合进入 fastboot，作者通过写入这个命令，让设备刷完后自动进入 fastboot，方便后续操作。

> 注意：rawprogram0.xml 中 misc 分区声明为 2048 扇区（1MB），但实际文件只有 13 字节。Firehose 烧录时只写入前 13 字节，剩余区域保持原样或补零。

### 2.3 vbmeta.img / vbmeta_system.img（AVB 校验链）

| 维度 | 原版 vbmeta.img | 作者 vbmeta.img |
|---|---|---|
| 大小 | 8 KB | 64 KB |
| AVB0 魔术字 | **未找到**（加密/签名头） | 标准 `AVB0`（偏移 0） |
| 字节序 | — | 大端序（AVB 标准） |
| algorithm_type | — | **2 = SHA256_RSA4096** |
| flags | — | **0**（verification + verity 均开启） |
| 签名 | — | 有（512 字节签名） |
| 公钥 | — | 有（1032 字节自定义公钥） |
| rollback_index | — | 0 |

| 维度 | 原版 vbmeta_system.img | 作者 vbmeta_system.img |
|---|---|---|
| 大小 | 4 KB | 64 KB |
| AVB0 魔术字 | **未找到** | 标准 `AVB0` |
| algorithm_type | — | 2 = SHA256_RSA4096 |

**关键分析：**

1. **原版 vbmeta 是加密的**：整个文件找不到 `AVB0` 魔术字，前 32 字节是高通签名/哈希头（与 abl.elf、boot.img、misc.mbn 的头部模式一致）。

2. **作者 vbmeta 不是简单关闭校验**：
   - `flags = 0` 表示 AVB verification 和 dm-verity **都处于开启状态**
   - `algorithm_type = 2` 表示使用 **SHA256_RSA4096 签名算法**
   - 带有**自定义公钥**（1032 字节）和签名（512 字节）
   
   这说明作者是**用自己的 RSA 密钥重新签名了 vbmeta**，而不是用 `--disable-verification` 关闭校验。

3. **推论**：要让自定义签名的 vbmeta 通过校验，必须满足以下之一：
   - abl 中的 AVB 根公钥被替换成了作者的公钥
   - abl 中的 AVB 校验逻辑被 patch（跳过签名验证）
   - 由于原版 abl 是加密的无法直接对比，作者 abl 是否被 patch 需进一步逆向确认

### 2.4 abl.img（Android Bootloader）

| 维度 | 原版 abl.elf | 作者 abl.img |
|---|---|---|
| 大小 | 155,744 字节（~152 KB） | 1,048,576 字节（1 MB） |
| ELF 魔术字 | **未找到**（加密） | 标准 `7F 45 4C 46`（偏移 0） |
| ELF 位数 | — | 32 位 |
| 架构 | — | ARM（EM_ARM = 0x28） |
| 入口点 | — | 0x9FA00000 |
| 填充 | — | ELF 后零填充到 1 MB 分区大小 |

**关键分析：**

1. **原版 abl.elf 是加密的**：全文搜索不到 ELF 魔术字，前 32 字节是高通签名头（`A4 A7 0F 4B...`），与 vbmeta、boot 的加密模式一致。

2. **作者 abl.img 是解密后的标准 ARM ELF**：
   - 标准 32 位 ARM 可执行 ELF
   - 被零填充到 1 MB（abl 分区大小）
   - 数据段从偏移 0 一直延伸到约 0x26000（~152 KB），与原版去签名头后的大小吻合

3. **来源推测**：作者的 abl.img 可能来自：
   - 从运行中的设备内存 dump（运行时 abl 已被解密加载到内存）
   - 从其他未加密版本固件提取
   - 自行解密了原版 abl.elf

4. **是否被 patch？** 由于原版是加密的，无法直接字节对比。需要对作者 abl.img 进行逆向工程（Ghidra/IDA），检查 AVB 校验函数、解锁状态判断函数是否被修改。

### 2.5 boot.img（内核+ramdisk）

| 维度 | 原版 boot.img | 作者 boot.img |
|---|---|---|
| 大小 | 96 MB | 96 MB |
| 魔术字 | **非标准**（加密头 `9A AC 07 5F...`） | 标准 `ANDROID!` |
| kernel_size | 解析异常（273 MB，因头部加密） | 32,695,136 字节（~31 MB） |
| ramdisk_size | 解析异常（3 GB，因头部加密） | 1,474,300 字节（~1.4 MB） |
| page_size | — | 4096 |
| SHA256 | 90367827BA27466D... | 86FD9CDC33993734... |

**关键分析：**

1. **原版 boot.img 也是加密的**：头部不是 `ANDROID!`，而是高通签名头，导致 kernel_size/ramdisk_size 字段解析出荒谬的值。

2. **作者 boot.img 是标准 Android boot 镜像**：
   - kernel 约 31 MB（合理的 ARM64/ARM 内核大小）
   - ramdisk 约 1.4 MB
   - 与原版大小相同（96 MB），但内容完全不同

3. **修改内容推测**：boot.img 被修改的部分可能包括：
   - ramdisk 中修改 `fstab`（关闭 dm-verity）
   - ramdisk 中修改 `init.rc`（添加 root 权限、修改启动参数）
   - 内核命令行参数修改（`androidboot.verifiedbootstate=orange` 等）
   - 内核本身是否被 patch 需解包后对比

### 2.6 super.img（系统分区容器）

| 维度 | 原版 | 作者 |
|---|---|---|
| 格式 | **Sparse 分块**（super_1.img ~ super_5.img） | 单个原始镜像 |
| 总大小 | 2,377.58 MB（sparse 压缩后） | 3,584 MB（原始 ext4） |
| 分块数 | 5 个 | 1 个 |

**分析：**
- 原版使用 Android Sparse 格式分块存储（压缩后的稀疏镜像），刷写时由 Firehose 自动展开
- 作者将 super 转换为**非 sparse 的原始 ext4 镜像**（3.5 GB = rawprogram 中声明的 7340032 扇区 × 512 字节）
- 这意味着作者可能修改了 super 内部的 system/vendor/product 分区内容（如删除手机管家、修改系统框架等），然后重新打包

## 三、原版固件加密模式总结

通过对比分析，**原版固件中以下文件均采用统一的高通签名/加密头格式**：

| 文件 | 前 4 字节（签名头标识） | 标准格式魔术字 |
|---|---|---|
| rawprogram0.xml | （二进制加密） | `<?xml` |
| abl.elf | `A4 A7 0F 4B` | `7F 45 4C 46` (ELF) |
| vbmeta.img | `9A B4 01 3D` | `41 56 42 30` (AVB0) |
| vbmeta_system.img | （类似加密头） | `AVB0` |
| boot.img | `9A AC 07 5F` | `41 4E 44 52 4F 49 44 21` (ANDROID!) |
| misc.mbn | `DB E2 43 0D` | （结构化数据） |

**共同特征：**
- 前 32 字节是高通的哈希/签名头（每个文件标识不同，但结构一致）
- 签名头后跟着真实的镜像数据
- 这不是 AES 加密，而是**高通 Secure Boot 签名格式**（类似 mbn 的签名头），用于 bootloader 阶段验证镜像完整性

> 作者的所有镜像都**去掉了这个签名头**，还原为标准格式。这说明作者要么有解密/去签名工具，要么从运行时设备 dump 了已解密的镜像。

## 五、关键结论

### 5.1 这个方案做了什么
1. **解除 AVB 签名校验链**：用自定义 RSA 密钥重新签名 vbmeta/vbmeta_system，配合可能被 patch 的 abl，使修改后的 boot/super 镜像能通过启动校验
2. **修改 boot 镜像**：调整 ramdisk/内核参数，关闭 dm-verity，可能添加 root 权限
3. **修改 super 镜像**：可能删除/修改系统应用（如手机管家）、修改系统框架
4. **强制进入 fastboot**：通过 misc 分区写入 `boot-fastboot` 命令
5. **解密 XML**：使 QFIL 能执行自定义刷写脚本

### 5.2 这个方案没有做什么
1. **没有攻破高通 Secure Boot 根信任（XBL）**：XBL 仍然运行，只是不校验 abl 或 abl 被 patch
2. **没有修改 misc/devcfg 中的 BL 锁标记**：解锁状态是通过 abl 层面实现的，不是改硬件锁标记
3. **没有关闭 AVB verification flags**：vbmeta 的 flags=0，校验在形式上是开启的，只是用了自定义密钥

### 5.3 遗留问题与后续分析方向
1. **abl.img 是否被 patch？** 需用 Ghidra/IDA 逆向作者 abl.img，检查 AVB 校验函数、`is_unlocked()` 函数是否被修改
2. **boot.img 具体改了什么？** 需解包 boot.img，对比 kernel 和 ramdisk 差异
3. **super.img 内部修改了什么？** 需挂载 super，对比 system/vendor/product 分区文件差异（这是分析"家长验证"被如何处理的关键）
4. **作者的 RSA 密钥从何而来？** 是随机生成的新密钥，还是从其他地方获取的？

### 5.4 与"家长验证"问题的关联
用户之前提到解锁后仍弹出家长验证。从本分析看：
- super.img 被整体替换（3.5GB 非 sparse 镜像），作者**很可能已经在 super 中修改了系统框架或删除了家长验证相关组件**
- 但如果家长验证逻辑部分实现在内核模块或 vendor 私有守护进程中，仅修改 super 可能不够
- **下一步建议**：解包作者 super.img，搜索家长验证相关的包名/服务/so 库，确认作者是否已经处理，以及处理方式
