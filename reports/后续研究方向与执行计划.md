# ND03 后续研究方向与执行计划

> 基于 DeepSeek 评估报告（2026-10-07）的三个重大突破制定
> 核心转变：从"猜测加密/找 patch 痕迹"转向"代码级分析 devinfo 解锁机制"

---

## 一、已确认的重大突破（改变全局的事实）

### 突破1：固件镜像解密已完全解决
- **算法**：与 XML 同一套固定 XOR 密钥流（256 字节 key_table，双重 XOR，等效 16384 字节周期流）
- **规则**：
  - 文件 ≤ 32768 字节（0x8000）：整个文件被 XOR 混淆
  - 文件 > 32768 字节：只有前 32 字节被 XOR 混淆，其余本来就是明文
- **验证**：
  - abl.elf XOR 后与设备 dump abl_v101.img 逐字节相同（0 差异）
  - vbmeta.img 解密后 AVB 自哈希 MATCH（stored=computed=a3b8b727…）
  - rawprogram0.xml 解密后与已有 decrypted_v1.0.1/ 逐字节相同
- **结论**：所谓"super sparse 高通签名头 DB E2 43 0D" = 密钥流前 4 字节，不是签名头
- **意义**：不需要 EDL dump 就能从固件包直接得到所有明文镜像

### 突破2：abl 代码已可读（不是全加密）
- **结构**：ELF(ARM32 容器) → UEFI Firmware Volume → FFS file(type=0x0B) → GUIDED section(EFI LZMA GUID) → LZMA 解压 → PE32+ ARM64 镜像
- **PE 细节**：machine=0xAA64(ARM64)，ImageBase=0x0，AddressOfEntryPoint=0x1000，VA=文件偏移（base 0 加载即可，可直接拖进 Ghidra）
- **关键字符串（解压后 2076 条可读）**：
  - `"State: Unlocked, AvbSlotVerify returned %a, continue boot"` —— **解锁即容忍 AVB 失败的核心分支**
  - `"No bootable slots found enter fastboot mode"` —— flags=2 实验进 bootloader 的代码路径
  - `"Unsupport unlock bootloader: %r"` / `"Unsupport unlock bootloader critical : %r"` —— 标准解锁命令被移除的 stub
  - `"is_unlocked: %d"` / `"is_unlock_critical: %d"` / `"magic: %s"` —— devinfo 结构字段
  - `"--- XTCWriteDevInfo user key is not null , so we need clear it !"` —— **abl 内部存在写 devinfo 的函数**
  - `"assert fail: ops->read_is_device_unlocked != NULL"` —— 解锁状态通过协议读取
- **意义**：解锁判定、devinfo 格式、XTCWriteDevInfo 都可以静态分析

### 突破3：作者 abl 是官方 UserDebug 构建（不是手工 patch）
- **证据**：
  - 作者独有路径字符串：`/data1/home/integration/workspace/ND08_System_HLOS_UserDebug/bootable/bootloader/edk2/…`
  - stock 路径：`…/SW5100_System_HLOS_User/…`
  - 作者 .text 比 stock 大 0x7000（约 28KB），字符串多约 150 条
  - LZMA 压缩段大 12KB，解压后正好 +32768 字节
  - 证书/信任根与 stock 同源（两张 General Use XTC Key 1 证书逐字节相同）
  - vbmeta/镜像签名仍是原厂密钥（所以 XBL 才肯加载）
- **Attestation CA 有效期（版本指纹）**：
  - v1.0.1 原版：2024-05-09 ~ 2044-05-04
  - 作者 abl：2025-01-10 ~ 2045-01-05（介于 v1.0.1 和 v2.8.1 之间）
  - v2.8.1 原版：2025-03-24 ~ 2045-03-19
- **结论**：解锁能力是"构建变体（UserDebug）"的属性，不是某个被改的字节
- **意义**：无法自行复制这条路径（除非拿到同类 debug 构建或利用漏洞），但可以分析 release abl 是否接受正确格式的 devinfo

## 二、已被否决的方向（不要再投入时间）

| 方向 | 否决原因 |
|---|---|
| 镜像文件 AES/高通加密研究 | 不存在，是固定 XOR 密钥流 + 前 32 字节混淆 |
| 找作者 abl 的 patch 痕迹 | 不存在，作者 abl 是原厂 UserDebug 构建 |
| 去 32 字节签名头还原镜像 | 错误，必须 XOR 回去而不是删掉 |
| flags=2 vbmeta 单字节修改 | 已证明原理上不可能（vbmeta 自校验失配） |
| CVE-2026-24088 作为主力路线 | 公开利用链对 ND03 不适用（无 efisp/无 GBL/Android 11 无 GBL 机制），仅作观察项 |
| 手动制作 Magisk boot | 有 8 个致命缺陷，应用官方 magiskboot |
| 跨版本混刷 | 已证实会卡 logo/开不了机 |

## 三、后续研究方向（按优先级排序）

### 🎯 方向1：abl 解锁机制代码级分析（最优先）
**目标**：精确定位 release abl 的解锁判定逻辑，确认 v1.0.1 能否通过正确格式的 devinfo 解锁

**具体步骤**：

#### 步骤1.1：全量解密固件包，建立明文镜像库
- 把密钥流 + 32KB 规则写成通用解密脚本 `xtc_fw_decrypt.py`
- 解密 v1.0.1 和 v2.8.1 两个固件包的**所有文件**
- 建立明文镜像库：xbl/abl/vbmeta/boot/recovery/super/dtbo/全部 .mbn
- 验证：解密后的 abl/vbmeta 与设备 dump 逐字节相同

#### 步骤1.2：解压 abl，得到可分析的 PE32+
- 写 `abl_unpack.py`：ELF → FV → FFS → LZMA → PE32+
- 输出三个版本的解压载荷：v1.0.1 release、v2.8.1 release、作者 UserDebug
- 确认 PE 结构：ARM64, ImageBase=0, VA=文件偏移

#### 步骤1.3：Ghidra 分析 release abl（v1.0.1）
定位三处关键代码：

**(a) "State: Unlocked, AvbSlotVerify returned %a, continue boot" 的引用**
- 找到这条字符串的交叉引用
- 分析 unlocked 判定的条件分支
- 确认：unlocked 状态从哪里读取？（devinfo? TZ 协议? RPMB?）

**(b) devinfo 协议实现（ops->read_is_device_unlocked / DeviceInfo）**
- 找到 devinfo 的 magic 字面量（字符串比较 `"magic: %s"`）
- 确定 devinfo 结构的字段偏移和大小
- 分析"devinfo 无效（全零）时的默认行为"——当前 v1.0.1 devinfo 是全零，默认是 locked
- 确认：正确格式的 devinfo(is_unlocked=1) 是否能被 release abl 接受

**(c) XTCWriteDevInfo 函数**
- 找到 `"--- XTCWriteDevInfo user key is not null , so we need clear it !"` 的引用
- 分析它清理的 "user key" 是什么（很可能就是解锁凭据）
- 确认：写 devinfo 的代码路径是否在 release abl 中完整保留

**判定标准**：
- 若 release abl 接受"正确格式的 devinfo(is_unlocked=1)" → **v1.0.1 就能在不依赖任何泄漏镜像的前提下解锁**（最干净路径）
- 若不接受 → 必须靠 debug abl（作者方案）或其他漏洞

#### 步骤1.4：对比 release vs UserDebug abl 的解锁逻辑差异
- 对比三个版本解压载荷的关键函数
- 找出 UserDebug 构建在解锁逻辑上的具体差异
- 确认：UserDebug 的 unlocked 是硬编码还是也读 devinfo？

### 🎯 方向2：devinfo 正确格式构造与测试（高优先，依赖方向1）
**目标**：如果方向1确认 release abl 接受 devinfo 解锁，构造正确的 devinfo 并在 v1.0.1 上测试

**具体步骤**：
1. 根据方向1的分析结果，构造正确格式的 devinfo 镜像（4KB）
   - magic 字段
   - version 字段
   - is_unlocked=1 的偏移
   - 其他必要字段（is_unlock_critical, charger_screen_enabled 等）
2. EDL 刷入 devinfo 分区（start_sector=1373184, 8 扇区）
3. 重启到 bootloader，检查 `fastboot oem device-info`
4. 若显示 Device unlocked: true → 测试 `fastboot boot recovery.img`（TWRP）
5. 若成功 → sideload Dm.zip 获得 root

**注意**：之前手动写的高通标准 devinfo（magic"DEVICEINFO"+is_unlocked=1@偏移12）不生效，说明小天才的 devinfo 格式可能与高通标准不同，必须从 abl 代码中确认实际格式。

### 🎯 方向3：作者镜像 vs 原版明文镜像逐文件对比（中优先，方案3收尾）
**目标**：正式结案"作者镜像制作过程"，确认每个文件的具体修改

**具体步骤**：
1. 用方向1解密得到的 v2.8.1 明文镜像，与作者镜像逐文件对比：
   - abl：已确认是 UserDebug 构建（方向1已覆盖）
   - vbmeta：DeepSeek 已确认是原厂 v2.8.1 vbmeta（原签名），验证逐字节相同
   - boot：Magisk 重打包，对比 kernel 差异（989 字节差异来源？AnyKernel hexpatch？还是不同构建？）
   - super：原厂 + fstab 微调，对比 fstab.qcom 的具体修改
   - misc：13 字节 "boot-fastboot"（已确认）
2. 总结作者的完整制作流程和工具链
3. 确认：哪些修改是必须的，哪些是可选的

### 🎯 方向4：v2.8.1 firehose 异常分析（低优先，唯一例外文件）
**目标**：分析 v2.8.1 prog_firehose_ddr.elf 为什么不符合密钥流规则

**背景**：
- v1.0.1 firehose（548,864B）是明文 ELF，可通用刷两版
- v2.8.1 firehose（552,960B）既不是明文 ELF，也不被本密钥流解释
- 作者用 v1.0.1 明文 firehose 刷 v2.8.1 固件（firehose 通用）

**具体步骤**：
1. 分析 v2.8.1 firehose 的文件头和熵
2. 尝试其他解密方式（是否用了不同的密钥流？AES？）
3. 确认：v2.8.1 firehose 是否被单独加密？为什么？
4. 意义：理解小天才固件加密的完整机制（是否有例外文件）

### 🎯 方向5：EDL 工具链修正（辅助，按需）
**目标**：完善 EDL 读取能力，用于读活设备状态

**已知问题与修正**：
1. **点号卡住** = 主机侧设备获取失败（驱动绑定/PID 不在白名单），与内存类型/loader 无关
   - 修正：用 Zadig 把 05c6:9008 绑成 WinUSB/libusb
   - eMMC 不需要 `--memory=emmc`（eMMC 是默认路径）
2. **PID 9008→9084**：9084 = DIAG+QDSS+ADB+RMNET 复合设备（非 EDL），不在 edl 的 default_ids
   - 修正：清空/中性化 misc，每次操作后重新上电进 9008
3. **每次操作后重进重连**：Sahara/Firehose 会话本身是一次性的，高通标准行为
4. **Windows 读盘替代方案**：
   ```
   QSaharaServer.exe -u COM22 -s 13:prog_firehose_ddr.elf
   fh_loader.exe --port=\\.\COM22 --sendxml=rawprogram0.xml --search_path=<固件目录> \
       --convertprogram2read --memoryname=emmc --noprompt --showpercentagecomplete
   ```
5. **EDL 的真实价值**（现在明文镜像可直接从固件包得到）：
   - 读活设备状态（devinfo/misc/frp/slot 元数据）
   - 无固件包机型的 dump
   - 快速试刷

## 五、风险与注意事项

1. **变砖风险最高的是 EDL 写 abl/xbl**：abl/xbl 坏了可能连 EDL 都进不去；每次实验前备份相关分区，保留加密全量包 + 可用 programmer
2. **devinfo 写入风险**：错误格式的 devinfo 可能导致设备无法启动，但可以通过 EDL 恢复（刷回全零 devinfo）
3. **CVE 研究**：CVE-2026-24088 仅作观察项，不作为主力路线；只在自有设备验证
4. **应避免**：跨版本混刷、改 vbmeta 单字节、在 abl 未备份的情况下写 abl 分区
5. **法律/安全**：仅自有设备、不外传利用细节
